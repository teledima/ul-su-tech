# Бизнес-требования к аналитическому сервису рыночных ставок и прогнозирования тарифов

> *Документ содержит выжимку продуктовых требований платформы «Умная Логистика», необходимую для проектирования аналитических витрин (Вопрос 2), правил очистки данных (Вопрос 1) и пакетного ML-скоринга (Вопрос 3).*

---

## 1. Назначение сервиса
Аналитический сервис предназначен для расчёта рыночных ориентиров и прогнозирования транспортных ставок по автомобильным грузоперевозкам. Он помогает логистам, закупщикам и аналитикам:
* определить справедливый уровень ставки по маршруту перед запуском тендера или спот-заявки;
* оценить волатильность и сезонную динамику тарифа;
* сопоставить фактические цены закрытых перевозок с рыночным коридором и ML-прогнозом.

---

## 2. Базовые правила расчёта ставок

### 2.1. Источник рыночного факта
* В расчёт исторических рыночных показателей включаются только **фактические завершённые прямые перевозки** (`is_fact = true`, то есть `price_type IN (1, 2, 3, 4, 5, 9)`, `complex = false`) с корректными физическими параметрами (`price > 0`, `distance > 0`). Ставки торгов (`price_type = 6`, `is_fact = false`) в обязательный scope не входят.
* Статистические ценовые аномалии (`outlier_mark = true`) и плановые отгрузки будущих периодов исключаются из расчёта исторического рыночного коридора, чтобы не искажать ориентиры.

### 2.2. Единая валюта и НДС
* Базовый расчётный показатель платформы — **ставка в рублях РФ (`RUB`, код `643`) без НДС**, так как это единственная сопоставимая величина для контрагентов с разными налоговыми режимами.
* Сделки в иностранной валюте (`840` — USD, `978` — EUR) приводятся к рублям по официальному курсу ЦБ РФ на дату расчёта курса (`nearest_rate_date`). В production `nearest_rate_date` заполняется по `created_at`: последний курс `setting_date <= created_at`, а если такого курса ещё нет — последующий. Так как production-запрос не упорядочивает редкую будущую ветку, в тестовом решении требуется детерминированный выбор `MIN(setting_date) > created_at`. Если точного курса по сохранённой дате нет, строка не попадает в нормализованную витрину и должна быть отправлена в карантин или явно посчитана как пропуск; fallback по `loading_date` не используется.

### 2.3. Единицы измерения тарифа
Аналитическая витрина должна предоставлять рыночные ориентиры в двух ключевых разрезах:
1. **Ставка за рейс (`руб./рейс`)** — полная стоимость перевозки по маршруту (`price_rub`).
2. **Удельная ставка за километр (`руб./км`)** — отношение стоимости рейса к дистанции маршрута (`price_rub / distance`), позволяющее сравнивать направления разной протяжённости.

## 3. Ключевые аналитические разрезы

* Месячная строка строится по `price_dates.price_date`, поэтому долгосрочная заявка может присутствовать в нескольких месяцах. Прямое использование только `prices.loading_date` нарушает зерно источника.
* Дубли `cities.gc_id` устраняются выбором записи с минимальным `cities.id`. Для одной цены и одной стандартной группы кузова должна остаться только одна строка; отсутствие связи с `price_body_types` означает fallback на `prices.body_type`, а затем `Не указан`.

Расчёт карточки маршрута выполняется с помесячной гранулярностью в разрезе:
1. **Маршрут:** населённый пункт отправления (`loading_city`) $\rightarrow$ населённый пункт назначения (`unloading_city`).
2. **Унифицированная группа кузова (`body_group`):**
   * `Тент` (`std_id = 56`: коды `56, 57, 58, 59, 60, 61`);
   * `Рефрижератор` (`std_id = 4`: коды `4, 46, 47, 48`);
   * `Изотерм` (`std_id = 2`: код `2`);
   * `Борт` (`std_id = 15`: коды `1, 15`);
   * `Прочие` (спецтехника, контейнеровозы, самосвалы, тралы и др.) / `Не указан`.
3. **Весовая категория груза (`weight_category`):**
   * `G20T` ($\ge 30{,}0\text{ т}$), `FTL` ($[10{,}0;\ 30{,}0)\text{ т}$), `10T` ($[5{,}0;\ 10{,}0)\text{ т}$), `5T` ($[2{,}5;\ 5{,}0)\text{ т}$), `L5T` ($[0{,}5;\ 2{,}5)\text{ т}$), `OTH` ($< 0{,}5\text{ т}$).

## 4. Состав показателей витрины маршрута

По каждой аналитической ячейке сервис должен рассчитывать три группы метрик:

1. **Рыночный коридор ставок (за рейс и за километр):**
   * **Медиана (`P50`)** — основной рыночный ориентир, устойчивый к перекосам выборки;
   * **Нижняя и верхняя границы коридора (`P25` и `P75`)** — межквартильный диапазон, в который укладывается центральная половина рыночных сделок;
   * **Средняя ставка (`AVG`)** — справочный средний тариф по очищенной выборке.
2. **Сезонная и временная динамика:**
   * **`MoM %` (Month-over-Month)** — относительное изменение медианной ставки к предыдущему месяцу;
   * **`YoY %` (Year-over-Year)** — относительное изменение медианной ставки к аналогичному месяцу прошлого года.
3. **Доказательная база и надёжность (`Data Trust`):**
   * **`trips_count`** — количество уникальных закрытых рейсов в основе расчёта;
   * **`carriers_count`** — количество уникальных организаций-перевозчиков на маршруте (`price_type IN (3, 9)`);
   * **`cv_rate`** — коэффициент вариации тарифа ($\text{stddev\_samp} / \text{avg}$), отражающий разброс цен; при менее двух наблюдениях или нулевом среднем — `NULL`;
   * **`reliability_level`** — `HIGH` при `trips_count >= 30`, `carriers_count >= 5` и свежести не более 30 дней; `MEDIUM` при `trips_count >= 10`; иначе `LOW_DATA`. Для одинаковых календарных ячеек без строки сравнения `MoM`/`YoY` возвращаются `NULL`.

## 5. Пакетное прогнозирование тарифа (ML-контур)
* Для новых и плановых заявок система формирует **прогнозную рыночную ставку перевозчика** (`predicted_price_rub`) с учётом географии маршрута (регионов отправления и назначения), километража, типа кузова, тоннажа и календарной сезонности даты погрузки.
* Результаты пакетного скоринга сохраняются в хранилище данных для ретроспективного контроля точности модели (**Факт vs Прогноз**, абсолютная и относительная ошибка прогноза).
